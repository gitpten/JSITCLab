# SPEC.md — Система обліку замовлень дитячого табору

## 1. Опис проєкту

Розробити вебзастосунок для обліку дітей, їхніх батьків, змін дитячого табору та замовлень на участь у змінах.

Застосунок повинен забезпечувати перегляд інформації про кожну сутність у вигляді HTML-таблиці. Усі таблиці розташовуються на одній HTML-сторінці, а перемикання між ними здійснюється за допомогою табів (вкладок).

**Мета проєкту:** закріпити навички роботи з JavaScript, масивами об'єктів, DOM, обробниками подій і динамічним формуванням HTML-таблиць.

## 2. Предметна область

Предметна область — організація відпочинку дітей у дитячому таборі.

У системі виділено чотири основні сутності:

- Дитина (Child).
- Батьки або законний представник (Parent).
- Зміна табору (CampShift).
- Замовлення на участь у зміні (Booking).

Замовлення є центральною сутністю системи. Воно пов'язує дитину, її батьків або законного представника та обрану зміну табору.

Статус замовлення та статус оплати є властивостями замовлення, а не окремими сутностями.

## 3. Сутності та їхні характеристики

### 3.1. Дитина (Child)

Сутність зберігає інформацію про дитину, яка може відпочивати в таборі.

| Властивість | Опис |
|---|---|
| `id` | Унікальний ідентифікатор дитини |
| `firstName` | Ім'я |
| `lastName` | Прізвище |
| `middleName` | По батькові, необов'язкове поле |
| `birthDate` | Дата народження |
| `gender` | Стать |
| `notes` | Додаткові примітки, необов'язкове поле |

### 3.2. Батьки (Parent)

Сутність зберігає контактну інформацію одного з батьків або законного представника дитини.

| Властивість | Опис |
|---|---|
| `id` | Унікальний ідентифікатор |
| `firstName` | Ім'я |
| `lastName` | Прізвище |
| `middleName` | По батькові, необов'язкове поле |
| `phone` | Контактний номер телефону |
| `email` | Адреса електронної пошти |
| `relationship` | Ступінь спорідненості з дитиною |

Для навчального проєкту допускається зберігання одного контактного представника в кожному замовленні.

### 3.3. Зміна табору (CampShift)

Сутність описує окрему зміну дитячого табору.

| Властивість | Опис |
|---|---|
| `id` | Унікальний ідентифікатор зміни |
| `name` | Назва зміни |
| `startDate` | Дата початку зміни |
| `endDate` | Дата завершення зміни |
| `price` | Вартість участі |
| `capacity` | Максимальна кількість дітей |
| `description` | Короткий опис програми зміни |

### 3.4. Замовлення (Booking)

Сутність описує запис дитини на конкретну зміну табору.

| Властивість | Опис |
|---|---|
| `id` | Унікальний ідентифікатор замовлення |
| `parentId` | Ідентифікатор батьків або законного представника |
| `childId` | Ідентифікатор дитини |
| `shiftId` | Ідентифікатор обраної зміни |
| `createdAt` | Дата створення замовлення |
| `status` | Поточний статус замовлення |
| `paymentStatus` | Поточний статус оплати |
| `comment` | Додатковий коментар до замовлення |

Властивості `parentId`, `childId` і `shiftId` забезпечують зв'язок замовлення з іншими сутностями.

## 4. Статуси замовлення та оплати

### 4.1. Статус замовлення

Властивість `status` може набувати таких значень:

| Значення | Опис |
|---|---|
| `new` | Замовлення створене |
| `pending` | Замовлення очікує підтвердження |
| `confirmed` | Замовлення підтверджене |
| `cancelled` | Замовлення скасоване |
| `completed` | Участь дитини у зміні завершена |

### 4.2. Статус оплати

Властивість `paymentStatus` може набувати таких значень:

| Значення | Опис |
|---|---|
| `unpaid` | Не оплачено |
| `partially_paid` | Оплачено частково |
| `paid` | Оплачено повністю |
| `refunded` | Кошти повернено |

Статус замовлення та статус оплати є незалежними характеристиками. Наприклад, замовлення може бути підтверджене, але ще не оплачене.

## 5. Зв'язки між сутностями

У системі передбачено такі зв'язки:

- Батьки можуть оформлювати кілька замовлень.
- Одна дитина може мати кілька замовлень на різні зміни або в різні періоди.
- Одна зміна може містити багато замовлень на участь дітей.
- Кожне замовлення пов'язане з однією дитиною, одним контактним представником та однією зміною.

Зв'язки між сутностями реалізуються за допомогою ідентифікаторів.

Наприклад, значення `childId` у замовленні відповідає значенню `id` одного із записів у масиві дітей.

## 6. Функціональні вимоги

### 6.1. Загальна структура сторінки

Сторінка повинна містити:

- Заголовок вебзастосунку.
- Панель табів для перемикання між сутностями.
- Контейнер для відображення активної таблиці.

Необхідно реалізувати чотири таби:

1. Діти.
2. Батьки.
3. Зміни.
4. Замовлення.

Усі чотири таблиці мають бути розміщені в одному HTML-документі. Одночасно користувач повинен бачити лише одну таблицю.

### 6.2. Перемикання табів

Після натискання на таб:

- Активний таб змінюється.
- Таблиця відповідної сутності відображається.
- Інші таблиці приховуються.
- Перемикання відбувається без перезавантаження сторінки.

Для реалізації необхідно використовувати JavaScript та обробники подій.

### 6.3. Відображення таблиць

Кожна таблиця повинна містити:

- Заголовки стовпців.
- Рядки з даними відповідної сутності.
- Стовпці для характеристик, визначених у специфікації.

Дані зберігаються в JavaScript у вигляді масивів об'єктів.

Під час формування таблиць необхідно використовувати JavaScript для створення DOM-елементів і додавання їх до сторінки.

Для кожної сутності необхідно передбачити щонайменше три тестові записи.

### 6.4. Відображення зв'язків у замовленнях

У таблиці замовлень потрібно відображати інформацію, яка дає змогу зрозуміти, хто, для кого та на яку зміну оформив замовлення.

Замість самих лише ідентифікаторів `parentId`, `childId` і `shiftId` бажано показувати зрозумілі користувачеві значення:

- Ім'я та прізвище дитини.
- Ім'я та прізвище контактного представника.
- Назву зміни.
- Дати початку та завершення зміни.
- Статус замовлення.
- Статус оплати.

Для цього JavaScript повинен знаходити відповідні записи в масивах дітей, батьків і змін за їхніми ідентифікаторами.

### 6.5. Додавання нових записів

Для кожної сутності необхідно реалізувати форму додавання нового запису:

- Дитина.
- Батьки або законний представник.
- Зміна табору.
- Замовлення.

Форму можна розмістити у відповідній панелі сутності або відкривати після натискання кнопки «Додати». Структура форми повинна відповідати властивостям сутності, визначеним у розділі 3.

Вимоги до форм:

- Ідентифікатор (`id`) генерується застосунком автоматично і не вводиться користувачем.
- Обов'язкові поля позначаються у формі та перевіряються перед додаванням запису.
- Необов'язкові поля (`middleName`, `notes` і `comment`) можуть залишатися порожніми.
- Для властивостей з обмеженим набором значень використовуються елементи вибору з відповідними варіантами: стать дитини, ступінь спорідненості, статус замовлення та статус оплати.
- У формі замовлення користувач обирає наявні записи дитини, представника та зміни. У масиві замовлень зберігаються відповідні ідентифікатори (`childId`, `parentId` і `shiftId`).
- Для дат початку та завершення зміни перевіряється, що дата завершення не передує даті початку. Вартість і місткість мають бути числовими невід'ємними значеннями.
- Якщо обов'язкові дані відсутні або не проходять перевірку, запис не додається, а користувач бачить повідомлення про помилку.
- Після успішного додавання форма очищується, а відповідна таблиця оновлюється без перезавантаження сторінки.
- Після додавання замовлення у таблиці мають відображатися назви та імена пов'язаних записів відповідно до вимог підрозділу 6.4.

### 6.6. Збереження даних

Дані застосунку повинні зберігатися у браузері за допомогою `localStorage`, щоб додані записи залишалися доступними після перезавантаження сторінки.

- Під час запуску застосунок завантажує з `localStorage` масиви дітей, батьків, змін і замовлень.
- Якщо для сутності ще немає збережених даних, застосунок використовує її початкові тестові записи та зберігає їх у `localStorage`.
- Після успішного додавання запису оновлений масив відповідної сутності зберігається у `localStorage`.
- Після успішного редагування або видалення запису оновлений масив відповідної сутності зберігається у `localStorage`.
- Дані, відновлені з `localStorage`, використовуються для формування таблиць і списків вибору пов'язаних записів у формі замовлення.
- Помилки читання, розбору або запису даних у `localStorage` обробляються так, щоб застосунок міг повідомити користувача про проблему і не припиняв роботу без пояснення.

### 6.7. Редагування записів

Для кожної сутності користувач повинен мати змогу змінити дані запису без перезавантаження сторінки.

- Значення, доступні для редагування, відображаються у клітинках таблиці. Користувач натискає на значення, щоб перейти до його редагування.
- Для введення нового значення використовується поле форми, наприклад текстове поле або відповідний елемент вибору.
- Зміна зберігається після натискання Enter, кнопки підтвердження або переходу фокуса до іншої частини документа.
- Після збереження таблиця оновлюється, а змінений запис зберігається у `localStorage`.
- Якщо введене значення не проходить перевірку, зміна не зберігається, а користувач бачить повідомлення про помилку.
- Ідентифікатори записів та зв'язки між сутностями не повинні змінюватися під час редагування звичайних полів.

### 6.8. Видалення записів

Для кожного рядка таблиці потрібно передбачити елемент керування для видалення запису, наприклад іконку хрестика.

- Після видалення запис прибирається з масиву відповідної сутності, таблиця оновлюється без перезавантаження сторінки, а зміни зберігаються у `localStorage`.
- Перед видаленням потрібно перевірити, чи є інші записи, що посилаються на цей запис.
- Запис дитини, представника або зміни, на який посилається замовлення, видаляти не можна. У такому разі потрібно повідомити користувача, що запис використовується в іншій таблиці та його неможливо видалити.
- Для видалення замовлення достатньо прибрати відповідний запис із масиву замовлень.
- Після успішного видалення відповідна таблиця оновлюється без перезавантаження сторінки.

### 6.9. Синхронізація між вкладками

Якщо застосунок відкрито у кількох вкладках одного браузера з тим самим origin, зміни даних у будь-якій вкладці повинні автоматично відображатися в інших відкритих вкладках.

- Синхронізуються додавання, редагування та видалення записів для всіх чотирьох сутностей.
- Вкладка, у якій виконано зміну, зберігає її у `localStorage` та оновлює власний інтерфейс.
- Інші вкладки реагують на стандартну подію `storage`, перечитують змінений масив із `localStorage` та оновлюють відповідні таблиці й залежні списки вибору.
- Зміни сутностей дітей, батьків і табірних змін також оновлюють пов'язані дані та списки у формі бронювання.
- Подія `storage` не надсилається вкладці, яка зробила запис; її інтерфейс оновлюється під час локальної операції.
- Якщо ключ сховища видалено або його значення пошкоджене, застосунок обробляє це без аварійного завершення та показує зрозуміле повідомлення за потреби.
- Для синхронізації використовуються стандартні можливості браузера без сторонніх бібліотек, фреймворків або серверного компонента.

## 7. Технічні вимоги

- HTML використовується для створення структури сторінки.
- JavaScript використовується для зберігання тестових даних, формування таблиць і реалізації перемикання табів.
- CSS є необов'язковим. Дозволяється використовувати мінімальне оформлення або залишити сторінку без стилізації.
- Заборонено використовувати сторонні бібліотеки, фреймворки та готові рішення для реалізації табів і таблиць.
- Форми додавання, перевірку введених даних, обробку подій і оновлення таблиць необхідно реалізувати стандартними можливостями JavaScript без сторонніх бібліотек і фреймворків.
- Редагування та видалення записів, перевірку зв'язків між сутностями й оновлення таблиць необхідно реалізувати стандартними можливостями JavaScript без сторонніх бібліотек і фреймворків.
- Для збереження даних використовувати стандартний браузерний `localStorage`, без серверної бази даних і сторонніх бібліотек.
- Для синхронізації вкладок використовувати подію `storage` або інший стандартний браузерний механізм, щоб усі відкриті копії сторінки одного origin отримували додані, змінені та видалені записи.
- Після успішного редагування або видалення дані відповідної сутності необхідно оновлювати в `localStorage`.
- CSS для елементів редагування та видалення є необов'язковим; основною вимогою є робота JavaScript-логіки.
- Необхідно використовувати стандартні можливості HTML, CSS і JavaScript.
- Застосунок повинен працювати в сучасному браузері.
- Код проєкту має бути розміщений у публічному Git-репозиторії.

- [ ] Зміни зберігаються в `localStorage` і залишаються доступними після перезавантаження сторінки.
- [ ] У рядках таблиць є елемент керування для видалення запису.
- [ ] Запис, на який посилається замовлення, не видаляється; користувач отримує зрозуміле повідомлення.
- [ ] Після успішного видалення таблиця оновлюється без перезавантаження сторінки, а зміни зберігаються в `localStorage`.
- [ ] Додавання, редагування та видалення записів в одній вкладці автоматично відображаються в інших відкритих вкладках того самого застосунку.
- [ ] Після зовнішньої зміни оновлюються відповідні таблиці та списки пов'язаних записів у формі бронювання.
- [ ] Обробка міжвкладкових змін не створює циклів повторного запису або помилок інтерфейсу.
- [ ] Додані записи залишаються доступними після перезавантаження сторінки.
- [ ] За відсутності збережених даних використовуються початкові тестові записи.
- [ ] Не використано сторонніх бібліотек, фреймворків і готових рішень.
- [ ] Проєкт розміщено в публічному Git-репозиторії.
- [ ] У корені репозиторію присутній файл `SPEC.md`.

## 10. Результат роботи

Результатом має бути вебзастосунок для перегляду, додавання, редагування, видалення та локального збереження даних дитячого табору. Користувач повинен мати можливість перемикатися між таблицями дітей, батьків, змін і замовлень, додавати записи через відповідні форми, редагувати значення у клітинках і видаляти записи з урахуванням зв'язків між сутностями. Зміни повинні залишатися доступними після перезавантаження сторінки та автоматично синхронізуватися між відкритими вкладками застосунку.

Проєкт повинен продемонструвати вміння працювати з масивами об'єктів, властивостями об'єктів, зв'язками між наборами даних, DOM, створенням HTML-елементів і обробкою подій користувача.
